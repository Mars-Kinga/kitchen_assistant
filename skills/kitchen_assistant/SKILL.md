# AI 厨房助手 Skill

## 功能

`kitchen_assistant` 是单进程、多轮对话的厨房流程 Skill。它负责理解做菜需求、推荐候选、确认菜谱、标准化用量和步骤、逐步指导、本地计时、局域网状态展示与完成反馈。

目前没有直接控制机器人硬件；返回结构化结果，由 Runtime 的 `RuntimeExecutor` 调用语音、屏幕、动作、灯带和表情能力。控制台同样不提供火源、刀具或高温设备的远程控制。

## 触发方式

触发词定义在 `skill.json`，包括“厨房助手”“我想做”“我想吃”“我要吃”“菜谱”“不知道做什么”以及常见菜名和食材。`runtime_core.agent.SkillAgent` 还会识别包含食物词的烹饪问法和库存表达。

示例：

```text
我想做番茄炒蛋
教我做红烧排骨
我只有蘑菇和牛肉，不知道做什么
厨房助手，我有胡萝卜和鸡肉，能做什么菜
```

活动会话建立后，“1人”“正常”“第二个”“开始”“下一步”等短句会继续路由到本 Skill，直到用户输入 `再见`。

## 输入

入口：`scripts/run.py:run(arguments)`。

输入 Schema：`schemas/input_schema.json`。

```json
{
  "user_text": "用户本轮原始文本"
}
```

`user_text` 必须是非空字符串，不允许额外字段。人数、口味、食材、忌口、厨具、时间和难度均从多轮自然语言中解析并保存在进程内会话。

## 输出

输出 Schema：`schemas/output_schema.json`。

顶层固定字段：

- `route="skill_result"`
- `task_name="AI 厨房助手"`
- `kitchen_state`
- `session_active`
- `provider_mode`

单条反馈必须有 `speech` 或 `question`，并同时包含：

- `display`
- `robot_action`
- `led_effect`
- `expression`

一次返回多个连续反馈时使用 `steps` 数组，数组中每项都遵守同一五通道契约。候选、当前菜谱和当前步骤等通过可选元数据返回。

Runtime 会在调用前校验输入，在调用后及异步 `poll()` 返回时校验输出。违约结果不会进入执行器，而会转成安全错误反馈。

## 状态机

```text
IDLE
  ├─ COLLECTING_REQUEST
  ├─ COLLECTING_INGREDIENTS
  └─ COLLECTING_PREFERENCES
       → SEARCHING_RECIPES
       → PRESENTING_CANDIDATES
       → WAITING_RECIPE_CONFIRMATION
       → WAITING_MEAT_THAW（需要时）
       → COOKING ↔ PAUSED
       → COMPLETED / CANCELLED
```

`kitchen/session_store.py` 只保存会话数据并分发状态；需求收集、搜索展示、菜谱确认、烹饪步骤、计时交互分别位于 `recipe_collection.py`、`recipe_discovery.py`、`recipe_confirmation.py`、`cooking_flow.py`、`cooking_timer_flow.py`。`conversation_intents.py` 统一短确认词，`ingredient_vocabulary.py` 统一食材和忌口词汇。Provider 或 LLM 不能直接推进状态、结束计时或调用机器人能力。

## 菜谱来源

- `mock`：读取 `recipes/recipes.json` 和按文件名排序的 `recipes/catalog/**/*.json`；目录加载时拒绝重复 `recipe_id` 或菜名。
- `ai_generated`：配置 `DASHSCOPE_API_KEY` 后由千问 Chat Completions 生成。
- `local_cache`：读取 `recipes/generated/` 中已通过校验的生成菜谱。
- `web_search`：预留模式，当前未接通真实搜索。

本地固定目录当前包含 440 道菜，统一存放在 `recipes/catalog/`，包括肉类、蔬菜、水产、主食与汤、轻食与减脂；其中 90 道为参考 HowToCook 固定提交 `c05758fa661ac4efa0361a987b700a351a22159b` 的校订菜谱。`recipes/recipes.json` 仅保留菜品流程配置，避免基础菜谱重复。参考菜谱记录 `source_key`、`source_revision`、固定链接和许可证；`recipes/sources.json` 统一记录上游仓库和转换说明。运行时不访问上游。目录变更后运行 `python scripts/validate_recipe_catalog.py`，检查总数、来源、重复项、具体用量和 1/2/3 人份标准化。

Provider 始终先查询本地固定目录和已验证生成缓存；符合菜名、忌口、厨具和库存约束的本地结果优先复用。按确认食材推荐时，优先提供两份完整方案、最多三份；至少一份完整可做的方案就保留，不因数量不足或未覆盖全部食材而失败。本地部分匹配同样可复用，但不能要求用户额外准备非可选主食材。每个候选是一份备选用餐方案，可由两三道菜、汤或饮品组合：整套饭菜覆盖全部食材是优先目标而非硬门槛，按实际使用食材种数从多到少排序，准确列出“没用到”；不要求每一道菜用全部食材，不强行混炒。组合标题按制作顺序用“＋”列出菜名，各道步骤以 `【第1道】` 等数字前缀标明归属；一份 recipe 保存总配料和完整顺序步骤，共用调料分配用量之和须与总配料一致。两道组合可写 12–18 步，三道可写 18–30 步，不压缩新手细节。按菜名仍只生成一个候选。完整菜谱保存为按菜名命名的缓存文件，后续优先复用；人数变化由 `RecipeNormalizer` 缩放食材和步骤用量。

AI 生成不是网页搜索，不提供虚构 URL。Provider 调用失败时可回退本地 Mock；缺少有效完整详情的 AI 候选不会显示，也不会在用户确认后再次调用模型。

候选逐条校验：有一份有效详情就返回该份，丢弃不完整或违约的其他行，不要求全部候选一起通过。JSON 后续候选截断时，可通过 JSON 解码器取出前面完整闭合的候选对象，再走同样的配料、步骤、人数和忌口校验；不能补括号、补食材或使用半截菜谱。只有一个完整候选也无需为了凑数量再次调用模型；全部无效时才按原有时间预算定向纠错一次并尝试本地兜底。

按食材推荐时，照片仅表示用户确认要吃的食材，不表示完整厨房库存。默认已有食用油、盐、白糖、生抽、老抽、醋、料酒、蚝油、胡椒粉、淀粉、香油及葱姜蒜等常备调料；按菜品需要选用，仍在配料和步骤中列出准确用量。默认调料不追加到确认食材，不计入首个全食材方案的覆盖或排序，也不因未拍照而列为缺少。本地推荐、生成和纠错提示遵守同一规则。蜂蜜、黄油、奶油、啤酒、红酒、咖喱块等特殊配料不默认已有；忌口和 `unavailable_ingredients` 中明确缺少的食材/调料优先排除。

## 计时规则

`RecipeNormalizer` 只为确实依赖时间的操作保留或恢复 `duration_seconds`：

- 火候：预热、加热、煮、炖、焖、煎、烤、蒸、炸、焯、炒、收汁等。
- 等待：腌制、浸泡、泡发、静置、醒发等。

洗切、搅拌、普通调味和装盘不自动计时。

用户说“开始”“下锅了”“开始计时”等才启动当前步骤计时。带时长步骤尚未启动时，“下一步”“跳过”或明确完成语句不会直接推进；助手要求用户选择：

- “开始计时”：由本地计时器执行；
- “确认完成”：用户明确表示已自行计时并检查完成状态。

运行中的计时若要提前结束，也需要二次确认。计时到期只提示检查实际状态，不自动宣称已熟或自动推进。

## 腌制/浸泡期间的并行规则

只有后续步骤同时满足以下条件时才提供并行建议：

1. 它是菜谱中真实存在的后续步骤；
2. 可独立完成，不接触正在等待的肉类或食材；
3. 不重复当前步骤已经量取或加入的食材、调料；
4. 不提前热油、空烧锅、炒糖色、油炸或开始后续正式烹饪；
5. 例外仅允许在独立锅具中只烧清水。

用户确认并行准备完成后会记录其步骤索引；当前计时不会被打断，后续到达该步骤时再次确认后跳过。

没有合规候选时不启动并行流程，也不虚构“准备料酒/调料碗”等工作，统一提示：

```text
在这段时间里你可以同步做自己想做的事情，时间到了我会叫你～
```

`llm/prompts.py` 对 AI 菜谱提出同样约束，本地 `_parallel_prep_candidate()` 负责最终兜底。

## 局域网控制台

使用 `python robot_main.py --console --no-play` 在文字模式旁启动控制台；使用 `--console-only` 只运行控制台。默认监听 `0.0.0.0:18765`，同一局域网中的手机、平板和电脑可以访问启动日志给出的地址。

控制台提供：

- 机器人模拟状态、最后动作和屏幕文字；
- 摄像头在线/读取/异常状态与单帧预览；
- 当前菜谱、步骤进度和计时剩余时间；
- 手机拍照、本地图片上传和多模态食材盘点；
- 用户增删食材并确认后优先提供两份候选，至少一份完整可行方案就保留；优先全食材覆盖，允许部分没用到并如实注明。支持分区、分段或多菜组合，不强行混炒；优先复用本地结果，AI 候选逐条通过完整配料和实际步骤校验。
- 搜索或浏览本地菜谱，打开完整配料与步骤，并从控制台直接选择进入做菜流程。

肉类或水产菜谱开始前统一展示“确认食材状态”，普通本地、AI 和视频菜谱遵守同一入口规则。主操作显示“新鲜或已完全解冻，开始”，用户明确确认后从第 1 步开始，不直接跳到第 2 步；暂停时主操作为“恢复指导”，恢复不推进。结束当前任务会清除当前菜谱、步骤、计时和待确认状态，保留候选以便选择其他菜；前后端都禁止在已取消、未确认食材或暂停状态直接切换步骤。按钮请求进行中禁用重复推进，轮询不能再次解锁。

图片通过内存中的 Data URL 处理，不落盘；单张图片限制 8 MB。写接口执行同源检查，控制台不提供高风险设备控制接口。

## 能力边界

- 不判断食材是否变质、食物是否熟透、是否含过敏原或能否安全食用；
- 不判断设备、燃气、火源或现场环境是否安全；
- 不提供起火、燃气泄漏、触电、受伤等事故的具体处置方案；
- 事故类输入只返回“超出功能范围”，暂停当前指导，并提示寻求现场专业人员或当地紧急服务；
- 多模态模型只盘点清晰可见的食材；不确定物品单独列出，必须由用户确认；
- 无候选、Provider 超时、AI JSON 错误、缓存写入失败和问答服务不可用均有本地降级路径。

## 依赖

运行依赖由项目根目录 `requirements.txt` 管理，测试依赖由 `requirements-dev.txt` 管理。主要外部包包括：

- `openai`：千问 OpenAI 兼容 Chat Completions；
- `opencv-python`：Mac 摄像头单帧拍摄与 JPEG 压缩；

- `numpy`、`scipy`、`sounddevice`：语音采集链路；
- `edge-tts`、`pyttsx3`、`pygame`：语音播放链路。

厨房文字流程和默认测试不需要网络或 Key。

## 配置

千问：

- `DASHSCOPE_API_KEY`
- `QWEN_BASE_URL`
- `QWEN_TEXT_MODEL`（默认 `qwen3-omni-flash`）
- `QWEN_VISION_MODEL`（默认 `qwen3-vl-flash`）
- `QWEN_TIMEOUT_SECONDS`（默认 `25` 秒）
- `QWEN_VISION_TIMEOUT_SECONDS`（默认 `20` 秒）
- `QWEN_MAX_RETRIES`（默认 `0` 次）

Key 可从环境变量或项目 `config/qwen.env` 读取，后者非空项优先。项目不会加载任意 `.env` 文件，真实 Key 不得提交或打包。迁移安装与启动见项目根目录 `START_HERE.md`。默认控制台端口为 18765，占用时连续尝试后续 19 个端口，可用 `--console-port` 修改。文字和视觉请求都关闭深度思考；文字使用流式接口并在客户端内聚合，普通问答限制输出长度。模型名称无效、权限不足或请求超时时会快速进入既有降级流程。

## 已知限制

- 会话只保存在当前 Python 进程，没有 `session_id` 和跨进程恢复。
- 只连接 Mock SDK，不含真实机器人能力 ID。
- 视觉能力可以使用 Mac 默认摄像头或控制台上传图片，只识别可见食材，不判断成熟度、过敏原或食品安全。
- `web_search` 未接通，AI 生成不等于联网搜索。
- 未开启语音功能，只有文字输入。
- 缓存目前按可读菜名组织，尚无过期时间和显式清理命令。
